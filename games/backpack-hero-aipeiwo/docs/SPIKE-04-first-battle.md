## 2. 三个测量 bug

### 2.1 致命一击被记成 0 伤害

敌人死时 `delta.enemies` 里是字符串 `"gone"` 而不是负数，
`_damage_from()` 只累加负数，于是**击杀那一下算出 0**。

第 2 步和第 16 步都是击杀，都记成了 `dmg=0`。

### 2.2 「打中被格挡」和「这物品没伤害」混成一谈

第 4/5/12/13 步敌人有护甲，打上去 **hp 不变、只有 block 变**。
而 `Snapshot.DiffJson()` **只输出 hp，不输出 block**，
所以 agent 眼里这四刀「什么都没发生」，账本老老实实记了 4 个 `dmg=0`。

这不是「运气差」，是**观测缺了一个维度**。

### 2.3 `state` 和 `delta` 的敌人标识符对不上

- `state.json` 的敌人 uid 是 `"e0"` / `"e1"`（数组下标）
- `ack.delta` 的敌人 key 是 `"e-12900"`（`GetInstanceID()`）

**两套 id 无法互相索引**。agent 拿到 `{"e-12900": -7}` 没法知道这是哪只怪，
更没法把 `"gone"` 换回它死前的血量（2.1 的修法就卡在这）。

根因是我在 `Snapshot` 里用了 instance id、在 `StateReader` 里用了下标，各写各的。

### 后果

账本：`damage_sum=46 / 13 次 = 3.54`，而木剑真实伤害是 7。
**低估了一半。**

策略据此算分：`score = 3.54 - 0.1×1 ≈ 3.44`。
分数偏低会导致它更早选择 `end_turn`，进而多挨打——
**测量误差直接影响了策略质量**，不只是报告难看。

## 3. 已修

| 问题 | 修法 |
|---|---|
| 2.1 击杀记 0 | `_damage_from(delta, pre_hp)`：`"gone"` 用**行动前血量**当伤害 |
| 2.2 格挡不可见 | `DiffJson` 增加 `enemies_block`；`Differs()` 也把护甲变化算进去 |
| 2.3 标识符不一致 | `StateReader` 的敌人 uid 改为 `"e" + GetInstanceID()`，和 delta 同源 |

账本同步增加 `absorbed_sum`：把「被挡掉的量」单独记，
以后可以算「这件物品打有甲目标的实际效率」。

> `"gone"` 换算成满血伤害是个**近似**：如果敌人是逃跑或自我销毁，会高估。
> 目前只在 `pre_hp` 里查得到才换算，查不到就不记（宁可少记，不可瞎记）。

## 4. 没解决的：游戏自带战斗统计读不到

`state.stats` 恒为：

```json
{"turn":{"damage_dealt":-1,"damage_taken":-1,"items_used":-1}, ...}
```

`-1` 是我的异常兜底值，说明 `GameFlowManager.GetCombatStat(type, length)`
每次调用都抛异常。枚举值已经确认过：

- `CombatStat+Type`: itemsUsed=0, damageTaken=1, damageDealt=6
- `CombatStat+Length`: turn=0, combat=1

已加诊断：下个版本的 probe 会把**真实异常消息**打出来
（`GetCombatStat THREW: ...`）。在拿到异常之前不猜。

> 这条本来是「白送的交叉校验」，现在变成待办。
> 它和 delta 是**两套独立观测**——如果两边对不上，就说明其中之一在撒谎。
> 这正是 A4「静默失败漏检 = 0」最想要的那种冗余。

## 5. 这场「赢」到底说明了什么

说明了：**状态读取 → 决策 → 执行 → 校验 → 记录** 这条链路是通的。

不代表：策略有智能。这场的实际策略是「有能量就用木剑，没能量就过回合」，
赢在木剑 7 点伤害 > 敌人单轮 9 点但分摊到两个敌人。
换句话说，**它赢了数值，没赢决策**。

想验证「智能」要到 L2：一步前瞻 + 敌人意图 + 效果账本。
现在意图已经能读到（`attacks: [{type, power}]`），但策略里还没用它。
例如第 3 步敌人意图「挡16+攻9」，正确做法可能是先打小怪而不是硬砍有盾的。
