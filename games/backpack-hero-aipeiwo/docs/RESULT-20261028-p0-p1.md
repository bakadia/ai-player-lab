## 0. 一句话

宝箱现在能打开了：`diag_event` 定位到三个门（GetRelevantEvent=null、`open` 属性存在、
Chest 不在房间下），`open_chest` 用 `RemoveEventProperty(open)` + `Play()` 生成 Chest、
补 `gameManager` 后调 `OpenChest()`；真机一次开箱 `items_total +4`、`items_loose +4`。
战利品能捡、能活过战斗；但 **v8.5 的 `place_item` 默认把 parent 设成 `Items`（包外容器）**，
所以物品虽然“在 Items 里、能用”，并没有进 13 格主背包。用户手动把物品拖进背包后
parent 变成 `Grid Parent`、cells 落在背包坐标内、`free_squares=1`——这证明正确的
parent 是 **`Grid Parent`**，v8.6 的 `via=bag` 已改成它（尚未部署）。

## 1. P0：宝箱链路

### 1.1 四个真正的卡点（都在真机上用 `diag_event` 看到）

| # | 现象 | 原因 |
|---|---|---|
| 1 | 站在宝箱房，`start_event` 仍 no-op | `DungeonPlayer.GetRelevantEvent(player.position)` 返回 **null**；IL 里 `StartEvent()` 第一行就是它，null 直接 return |
| 2 | 即使拿到事件，`Play()` 也不生成宝箱 | 事件自带 `open` 属性（值 0）；`Play()` 只看 `GetEventProperty(open)` **是否存在**，不读值 → 直接 return |
| 3 | `room.GetComponentsInChildren<Chest>()` 找不到宝箱 | `Play()` 把实例挂到 `Player.main.transform.parent`，不是 `DungeonRoom` 子节点 |
| 4 | 找到 Chest 后 `OpenChest()` NRE | `Play()` 刚实例化的 Chest 还没跑 `Start()`，`gameManager` 字段是 null；`OpenChest()` 第一段就读 `gameManager.floor` |

另外确认：`Chest.OpenChest()` 在生成 loot **之前**就 `FinishEvent()`；一旦 NRE，
事件会变成 `finished=true` 但没有战利品。所以第 4 条必须在调 `OpenChest()` 之前补。

### 1.2 动作

- **`diag_event`（只读）**：输出 player/room、`GetRelevantEvent` 结果、房间内所有
  `DungeonEvent`（type/finished/itemsToSpawn/open/mimic）、房间内和全局 Chest
  （isOpen/type/numOfItems/startingItems/dungeonEvent 绑定/gameManager）、
  `GridSquare.allGrids` 的逐格坐标/占用/TestForItem。ack 里在 `diag` 字段。
- **`open_chest`**：
  1. 找当前房间未完成的 Chest 事件；
  2. 先找已有 Chest（全局，按 `dungeonEvent == ev` 或事件位置近）；
  3. 没有才 `RemoveEventProperty(open)` + `Play()`，再从全局找新生成的 Chest；
  4. 补 `dungeonEvent`、补 `gameManager = GameManager.main`；
  5. `chest.OpenChest()`。
- `MapProbe.WriteLegal` 在 Chest 事件时增加 `open_chest`；`loop.py` 地图分支优先选它。

真机结果（`data/runs/chest-open-v85-20261028.json`）：

```
open_chest ok=True changed=True ms=702
delta={"luck_uncommon":3.6,"luck_rare":1.8,"luck_legendary":0.54,
       "items_total":4,"items_placed":4,"items_loose":4}
```

开箱后 `legal` 立刻出现 4 个 `place_item`（FLOATY / CANDY APPLE / TAI CHI RULER / SUN RAY RAPIER）。

## 2. P1：战利品摆放

### 2.1 改了什么

- `place_item` 增加 `via=fit`：
  - 用 `GridSquare.allGrids` 的空格 + 物品 collider 形状（`GetGridPositionsAtPosition`）
    找候选；形状算不出来时按游标轮转空格。
  - 连续放多件时用 `_placeCursor` 轮转，避免都塞进第一个格子。
  - 默认路径先把 `parentInventoryGrid` 设成 `GameManager.inventoryItemsParent`，再
    `StartDrag → 位置 → EndDrag`。
- `StateReader`：`backpack` 增加 `grid_squares` / `free_squares`，`unplaced[]` 增加 `cells` /
  `parent`；`backpack.items[]` 增加 `parent` / `last_parent`。
- `MapProbe.WriteLegal`：地图阶段有 loose 物品且有空位时给 `place_item`。
- `loop.py`：地图/战斗都支持 `place_item` 失败后换候选（`skip=1`）重试一次；
  地图分支优先 `open_chest`。

### 2.2 真机结果（重要：v8.5 代码放的是包外 Items）

4 件战利品 `place_item ok=True changed=True`（各约 500 ms），但 cells/parent 是：

| 物品 | cells | parent | 实际位置 |
|---|---|---|---|
| FLOATY | `4,2` | Items | 包外 |
| CANDY APPLE | `4,2` | Items | 包外 |
| TAI CHI RULER | `3,0`, `3,1` | Items | 包外 |
| SUN RAY RAPIER | `4,-1`, `4,0`, `4,1` | Items | 包外 |

`items_in_grid` 确实 +1，物品也能用/能活过战斗，但 **背包画面是空的**：`Items` 是包外容器。
所以 P1 的“入包成功”要降级为“物品没丢，但没进主背包”。

用户手动把物品拖进 13 格背包后，同一个 state 变成：

| 物品 | cells | parent |
|---|---|---|
| DYNAMITE | `1,2` | **Grid Parent** |
| WOODEN SWORD | `-1,-1`, `-1,0`, `-1,1` | Grid Parent |
| ROUGH BUCKLER | `0,0`, `0,1`, `1,0`, `1,1` | Grid Parent |
| ENGINE WAND | `0,-1`, `1,-1` | Grid Parent |
| SHIV | `2,-1` | Grid Parent |
| TOXIC KUNAI | `1,-2` | Grid Parent |

`grid_squares=13, free_squares=1`，唯一空格是 **`(2,-2)`**（用户“留了个空位”）。
证据：`data/runs/bag13-manual-20261028.json`、`state-v85-bag13-manual.json`。

**结论：主背包的 parent 是 `Grid Parent`，不是 `GameManager.inventoryItemsParent`（Items）。**
v8.6 的 `place_item via=bag` 已改成 `GridSquare.transform.parent`，**已部署并真机试过**：
3 个教程物品的 parent 确实是 `Grid Parent`，但 cells 仍是 `-6,2 / -5..-4`（包外）、
`free=9`。原因见 §2.3：`EndDrag()` 会把物品拉回 `startPosition`，目标格被忽略。

### 2.3 为什么“设 parent + 移到目标格 + EndDrag”还不够

`ItemMovement.EndDrag()` 的 IL 第一段：

```
transform.position = startPosition;
transform.rotation = startRotation;
AddToGrid(false);          // -> GetGridObject() + GridObject.SnapToGrid()
```

`place_item` 现在是 `StartDrag → transform.position = target → EndDrag`，
EndDrag 会把物品**重置回 startPosition**（掉落区）再 AddToGrid；parent 设对也没用。
下一步应改 `ItemMovement.startPosition` 到 target（或调 `MoveItemTowardsGrid`），
而不是改 transform。详见 `HANDOFF-NEXT-20261028-2200.md` §3.3。

## 3. 还没解决的（P1 的边界）

1. **`GridSquare.allGrids` 就是主背包**：升级后 13 格，和用户截图完全一致；
   之前的 9 格是升级前的 3×3，不是 pouch。
   - 手动拖入后 `free_squares=1` 是准的；但 v8.5 代码路径放 Items 时 `free_squares=13`，
     因为包外物品不占主背包格。
   - v8.6 的 `via=bag` 已真机验证 parent 正确，但 cells 仍在包外（EndDrag 重置
     `startPosition`）；下一步改 `startPosition` 或 `MoveItemTowardsGrid`，再验收。
2. **背包满了怎么办**：13 格里已占 12 格，只剩 `(2,-2)`；地上还有 4 件
   （ARROW、POULTICE×2、DISGUSTING FOOD），最多再放 1 件。没有 move/rotate/drop，
   其余 3 件只能放弃。P2.2 必须先补这些动作。
3. **单格叠放**：v8.5 在 `4,2` 叠了 FLOATY/CANDY APPLE，但那是包外，不代表主背包允许叠；
   主背包的叠放/占用还要用 v8.6 真机验证。
4. **CANDY APPLE ≠ handoff 的 CANDY**：它只给 heal 8，没出现 `max_hp`/`luck` 回执。
   玩家侧 `status` 样本仍只有之前的 `fire`/`regen`。
