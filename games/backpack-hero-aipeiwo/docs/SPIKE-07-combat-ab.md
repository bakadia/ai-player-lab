# SPIKE-07 · 战斗决策离线 A/B（贪心 vs 枚举）

> 2026-10-27 · 起因：`policy.py` 是逐步贪心，怀疑它不是「不会算」，是「算法形状不对」。
> 结论先行：**在完全相同的估值函数下，只换决策过程，回合价值差 13.6%；两处 3 行改动能收回 2/3。**

## 0. 一句话结论

| 决策过程 | 改动量 | 回合价值缺口 | 一回合零伤害 |
|---|---|---|---|
| `greedy`（现状） | — | **13.6%** | 19.0% |
| `greedy_ratio`（按每点能量选） | ~4 行 | 14.1% | 26.8% |
| `greedy_aware`（记住已挡掉的伤害） | 1~3 行 | **10.3%** | 11.9% |
| `greedy_ratio_aware`（两处都改） | ~6 行 | **4.9%** | 10.4% |
| `enumerate`（单回合精确解） | ~120 行 | 0（定义） | — |

（n=7200 个合成局面，`plain`+`blocky` 两种组合，linear/steep 两条费用曲线各半。）

**所以「最优战斗」不是靠更强的估值函数，是先把它从「逐步贪心」换成「按回合算」。**
但也不是必须一步到位上求解器：先打两个补丁，就能收回大部分。

---

## 1. 先说数据：真实日志做不了这件事

跑之前先查了现有日志，结论是**都不含决策所需的信息**：

| 文件 | 内容 | 能不能做 A/B |
|---|---|---|
| `data/state-log/*.jsonl` | 探针快照：`enemies`/`items_in_grid` 是**计数**，`legal` 只有动作**类型名**（`["use_item","use_item","end_turn"]`） | ✗ 没有 uid、费用、敌人血量 |
| `data/runs/*.jsonl` | `decide` / `act` 事件：动作 + delta + 理由字符串 | ✗ 只有被选中的那一个动作，没有候选集 |
| `data/items.json` | 账本只有 2 个条目（`WOODEN SWORD` 30 样本、`MEAL` 1 样本） | ✗ 太薄 |

`runtime/state.json` 的 schema 是够的（`backpack.items[].energy_cost`、`enemies[].attacks`、`legal[]` 带 uid），
但那是**单帧**。所以这次用合成局面做机制验证，同时把脚本写成能吃真实快照（`--mode snapshot --stats`），
等日志补齐就能直接跑。

> 顺带一个发现：`state-log` 是探针写的，**决策所需字段根本没落盘**。要复盘决策，得让 loop 把
> 「当轮完整 state（含 legal 的 uid/energy）+ 选中的动作 + 候选分数」一起写下来。这是后面所有分析的原料。

## 2. 方法：把「估值」钉死，只换「决策」

三种策略**共用同一个估值函数**（直接复用 `policy.py` 的 `score_action`，账本用固定表冒充），
所以差异 100% 来自决策过程：

- `greedy`：复刻 `policy.choose` 的主循环（每步取当前分最高的动作，选完再算）。
- `greedy_ratio`：同样打分，但按 `分数 / 费用` 选。
- `greedy_aware`：同样打分，但每步把**已经挡掉的伤害**从 `incoming` 里扣掉再算格挡价值。
- `enumerate`：单回合精确解（DP，状态 = 能量 × 敌血 × 格挡 × 增伤 × 已用件）。

评价不用它们自己的分数，用**回合终局价值**：

```
V = 有效伤害（打到活敌人身上的，溢出不算）
  + 0.8 × 有效格挡（min(累计格挡, 还活着的敌人的总攻击)）
  + 1.0 × 击杀折价（被杀掉的敌人「这回合原本要打我们多少」）
  - 0.1 × 消耗能量
```

击杀折价那项是必须的：没有它，「留 1 血不杀、把能量拿去套盾」会被算成更优——那不是游戏里的最优。

合成局面的假设（全部可调，写在 `CURVES` / `MIXES` 里）：

- 3 能量、3/6/10 件物品、1~2 个敌人、敌人 8~16 血 / 3~7 攻；
- 费用曲线 `linear`（伤害与费用成正比）与 `steep`（便宜货更划算）各跑一半；
- `plain`（纯攻防）、`blocky`（盾多）、`mixed`（掺 5% 本回合增伤）。

## 3. 结果

### 3.1 主表（plain + blocky，n=7200）

| 决策过程 | gap | 零伤害回合 | 直接最优 |
|---|---|---|---|
| greedy | 13.6% | 19.0% | 52.3% |
| greedy_ratio | 14.1% | 26.8% | 60.6% |
| greedy_aware | 10.3% | 11.9% | 58.9% |
| greedy_ratio_aware | 4.9% | 10.4% | 73.8% |

两个反直觉的点：

1. **只改「按每点能量选」会更差**（13.6 → 14.1，零伤害 19% → 27%）。因为盾通常更便宜，
   按性价比排序会把能量全喂给盾——**必须先修「格挡饱和」，再谈性价比**。
2. **物品越多，贪心反而不一定更差**（10 件 / 1 敌人时只差 3.5%）：替代品多了，
   选错一件的代价被摊薄。真正拉开差距的是**两个敌人**（最高 24%）——那里有击杀顺序。

### 3.2 敏感性

| 设置 | greedy | aware | ratio_aware |
|---|---|---|---|
| 基准（w_block 0.8，含击杀折价） | 13.6% | 10.3% | 4.9% |
| 关掉击杀折价（w_kill 0） | 12.6% | 9.0% | 5.5% |
| 格挡只值 0.4（w_block 0.4） | 18.7% | 15.1% | 9.2% |

排序在所有设置下不变；**格挡越不值钱，贪心越差**——因为它的错误正是「过度买盾」。

### 3.3 三个能拿去讲给人听的案例

**① 全程套盾，一点伤害不打**（`linear/plain/i3`，敌人 11 血 / 来袭 6）：

```
物品：盾 1费4挡、盾 2费5挡、剑 1费4伤
greedy  : 盾(4) → 盾(5) → 结束     伤害 0，格挡 9（有效 6，浪费 3）
精确解  : 盾(4) → 剑 → 剑          伤害 8，格挡 4（有效 4）
```

**② 杀一个敌人值多少钱**（`linear/mixed/i10/e2`，两个 6 攻的敌人）：

```
greedy  : 伤害 4，零击杀，格挡 9     V=10.9
精确解  : 伤害 27，两个全杀          V=38.7
```

贪心的打分里「杀掉一只」没有独立价值，只有「清场」才有 +100；所以它不会为了少挨一轮去补刀。

**③ buff 物品它根本不会用**（`mixed`，42 个含「本回合增伤」的样例）：

```
greedy 用过增伤物品：0 / 42
精确解 用过增伤物品：33 / 42
```

原因很直接：`score_action` 对「0 伤害 0 格挡」的物品给 0 分，`choose` 见到非正分就 `end_turn`。
**投资型动作在现在的框架里是不可见的**，不是算错，是没进入候选。

## 4. 建议

**第一步（今天就能做，2 处小改，不改架构）**

```python
# policy.py :: score_action
# 之前
incoming = incoming_damage(state)
# 之后：把已经买到的格挡扣掉，否则每面盾都按「全额来袭」估值
incoming = max(0, incoming_damage(state) - int(state.get("player", {}).get("block") or 0))
```

```python
# policy.py :: choose
# 按「每点能量的分数」选，而不是绝对分数（必须和上面那条一起上，单独上会更差）
s_norm = s / max(1, int(action.get("energy", 0)))
if s_norm > best_score:
    best_score, best, best_why = s_norm, action, why
```

预期：13.6% → 5% 上下，零伤害回合 19% → 10%。
**验收方式**：用本脚本的 `--mode snapshot` 在真实战斗快照上跑一遍；再拿 `data/runs` 里
「同一局面的两种选择」做人工抽检。

**第二步（要动 Bridge / 模型）**

- 给 `legal` 加 target（现在点物品是游戏自己决定打谁，击杀顺序控制不了）。
- 把「击杀折价」写进打分（`该敌人每回合输出 × 预计剩余回合`），并把 `lethal_bonus` 从「清场」改成「单杀」。
- 把回执升级成结构化事件（谁打谁、被挡多少、上了什么状态），否则估值永远只能靠名字均值。

**第三步（做完前两步再谈）**

单回合枚举器（本脚本的 `enumerate_turn` 就是原型，~40 行）。
它的边际收益 = 剩下的 ~5%，而且**前提是效果模型准确**——模型错，搜索只会更自信地选错。

## 5. 局限（别把这里的数字当成游戏结论）

1. **合成局面**，不是真实对局；曲线与组合比例都是假设，只用来比较「决策过程」。
2. **单回合**，没有「这一回合的投资下回合兑现」（毒、怒气、成长），所以会低估投资型打法。
3. **不能选目标**（`legal` 没有 target），击杀顺序只能靠「打血最少的」近似。
4. **没有状态效果、没有布局加成、没有多段攻击**；账本被假设为精确已知。
5. 评测函数本身有权重（0.8 / 1.0），换权重结论的**排序**不变，但**绝对值**会变。
