# REFERENCE · 战斗「最优解」资料调研

> 2026-10-27 · 触发：新卡点「AI 不会打最优战斗」。
> 目的不是给结论，是给**可验证的形状**：这个游戏的战斗到底是什么问题、别人怎么解同类问题、我们现在差在哪。
> 所有 wiki 数值都标了来源；**标「待实测」的一律不要当事实用**。

## 0. 结论先行

1. **这不是「打牌」，是小规模确定性调度问题。** Purse/Satchel 没有抽牌，背包里的物品全都在手上，
   唯一的稀缺资源是每回合 3 点能量；敌人意图全公开。所以单回合的动作空间是「用哪些物品、按什么顺序」，
   规模在几百到几千，**可以直接穷举到最优**，不需要 MCTS、不需要 RL。
2. **「最优」的天花板不在搜索，在效果模型。** 800+ 物品、布局加成（相邻/对角/行列/朝向/浮沉/锻造）、
   状态时序（毒在回合末、灼烧可挡、尖刺反弹）。模型错一点，搜索只会更自信地选错。
3. **人类攻略的共识只有三条**：先算斩杀 → 只挡「这回合真的会打到你」的那部分 → 剩下的能量全部换成伤害/成长。
   这三条正好对应一个「斩杀检查 / 死亡线检查 / 余量最大化」的三段式回合结构。
4. **外部最相关的两个工作直接印证我们的判断**：
   - *Stack-Aware Enemy AI*（I3D'26）在一个「带持久堆叠的战斗」的卡牌 roguelike 里证明：
     **lookahead + 空间感知 > 加权概率启发式**——后者正是我们现在的 `policy.py`。
   - *SpireBench*（arXiv 2610.12596）测了 20 个 LLM 打完整《杀戮尖塔》，结论是
     **强弱的分水岭就是「每一场战斗打得好不好」**，且模型普遍「过度保血、不愿用血换成长」。
5. **我们现在的 `policy.py` 有三个结构性缺陷**（§6）：按名字估值、按绝对分选动作、看不见击杀与投资。
   其中「逐步贪心」已在 `SPIKE-07` 里量化：同一套估值下差 **13.6%** 的回合价值，
   两处 3~6 行的改动能收回 2/3（→4.9%）；剩下的才是求解器的价钱。

## 1. 战斗的结构性事实（决定算法形状）

| 事实 | 来源 | 对算法的含义 |
|---|---|---|
| 每回合 **3 能量**（Purse/Satchel/Tote/CR-8；Pochette 只有 2） | [namu wiki §3.2](https://m.namu.moe/w/%EB%B0%B1%ED%8C%A9%20%ED%9E%88%EC%96%B4%EB%A1%9C)；[9game](https://www.9game.cn/beibaoyingxiong/11512431.html) | 能量是唯一硬约束 → 组合优化 |
| **没有抽牌**：背包里的物品每回合都在，只是付不起费就变暗 | namu §3.4；[Atlas](https://backpackhero.wiki.gg/wiki/Atlas) | 动作空间 = 物品子集 × 顺序，可与「手牌随机」解耦 |
| **格挡不留存**：下个自己回合开始时清零 | namu §3.1；9game「本回合有效，不能留到下一回合」 | 超挡 = 100% 浪费；格挡是「本回合的保险」，不是资产 |
| **敌人意图全公开**（头顶图标：剑/盾/钱/诅咒/召唤/上状态/什么都不做/逃跑） | namu §3.5 | 战斗是**完全信息**博弈 → 可精确规划 |
| 敌人伤害**随回合增长** | namu §3 | 存在「时钟」：拖越久越贵 → 斩杀价值随时间上升 |
| 毒：回合末结算、**无视格挡**、可被闪避；**毒 ≥ 敌人当前 HP 时该敌人跳过回合** | [Status Effects](https://backpackhero.wiki.gg/wiki/Status_Effects) | 毒既是伤害也是「软控」，是打高格挡/高尖刺的答案 |
| 灼烧：可被格挡/闪避；**当前版本对敌人结算时无视格挡（bug）** | 同上 | 对敌灼烧的估值要按「真伤」算，这是可利用的不对称 |
| 尖刺：被攻击时反弹，**远程/投射物免疫** | 同上；[Weapons](https://backpackhero.wiki.gg/wiki/Weapons) 的 Projectile 词条 | 打尖刺怪要用远程，否则每次攻击都在自伤 |
| 空间即卡组：相邻（接触即算）/对角/整行整列/朝向/浮沉/唯一性 | [18183 道具特质](https://m.18183.com/gonglue/202604/8922904.html) | 同一件物品的数值**取决于摆位** → 账本不能只按名字记 |
| 头盔必须在所在列**顶格**才生效；同类头盔/鞋子只有靠左的第一个生效 | 18183 | 「摆错 = 物品不存在」，这是 0/1 的价值，不是折扣 |
| 箭矢**与任何物品相邻就失效**（鼠木除外） | 18183 | 存在**刻意的负协同**，模型必须能表达「相邻 → 归零」 |
| 危险物：不处理就每回合直接掉血（越拖越痛）；**盖住物品 = 该物品被禁用** | namu §3.6 | 危险物是「用能量/空间换血」的第三类动作 |
| 战斗内重排消耗 **3 能量**（有遗物则 0） | namu §3.4 | 重排是「一整个回合」的机会成本，MVP 阶段建议先不建模 |

> 一句话：**能量买动作，空间买倍率，信息全公开，格挡不累积。** 这四条决定了最优解的形状。

## 2. 「最优」长什么样

因为格挡不留存、意图全公开，**一个回合的结局在你按下 end_turn 前就完全确定了**（前提：没有伤害随机）。
所以「最优战斗」可以拆成一个非常干净的三段式：

```
1) 斩杀检查：这回合能不能把敌人全清？（能 → 忽略格挡，全砸输出）
2) 死亡线检查：这回合会不会死？会 → 必须买到足够的格挡/减伤（硬约束，不是加权）
3) 余量最大化：剩下的能量，按「静态局面评估」选一组动作
```

第 3 步的形式化就是一个**带预算的集合选择**：

```
choose  multiset A of usable items
s.t.    sum(cost) <= energy
max     Eval(state_after_turn(A))
```

`Eval` 不需要很聪明，因为它只需要比较「同一回合的不同结尾」：
我方 HP、剩余格挡（=0，因为不留存）、每个敌人的 HP/状态/下回合意图、以及「还要几回合打完」。
这比《杀戮尖塔》简单一个量级——那边要处理抽牌随机，才需要 MCTS/期望。

**为什么不是 MCTS**：树太小（3 能量 × 十几个物品）、分支确定性、单回合可精确解。
MCTS 的价值在「采样不可解析的随机」，我们这里没有那个随机。真要多回合，用「浅层展开 + 静态评估」
（类似棋类的 quiescence）比蒙特卡洛更省、更好调、更好解释。

**唯一需要小心的**：动作之间有顺序依赖（先上 buff 再攻击、先减费再使用、先杀召唤者）。
所以枚举的必须是**序列**（或至少按拓扑约束排序的集合），不能当成无序集合。

## 3. 人类攻略里可抄的启发式

1. **看意图决定「套盾还是输出」**：敌人准备攻击且总攻击 > 你的格挡 → 花钱套盾；否则全部输出。
   （[9game 护盾篇](https://www.9game.cn/beibaoyingxiong/11512431.html) 原文就是这个判据）
2. **只挡「会打到你」的那部分**：格挡不留存，多挡一点都是浪费。（我们 `policy.py` 的 `min()` 已经对了）
3. **斩杀优先于换血**：早一回合杀掉 = 少挨一整轮，而且敌人伤害还在涨。
4. **毒是穿透答案**：无视格挡、无视尖刺，还能让「毒 ≥ HP」的敌人直接跳过回合。
5. **打尖刺怪换远程**：近战打尖刺 = 自己掉血，这是「伤害」估值的符号错误。
6. **投资 vs 兑现**：宝石/怒气/毒/成长类物品需要回合数才能回本；越早下越值，但下的时候要让出当回合的输出。

> 这 6 条其实全是同一个式子的不同项：`本回合收益 + 未来回合收益的折现 - 死亡风险`。

## 4. 构筑与设计原理（为什么这些启发式成立）

- **能量是唯一货币，所以一切都能归一化。** Scratch = 1 能量 3 伤害（namu §3.4），这是官方给的
  「基准兑换率」：**≈3 伤害/能量**。任何物品都能换算成「几个 Scratch」，这就是最强的先验。
- **Tempo vs Value**：低费高效 = tempo（现在兑现），成长型 = value（用回合数换指数）。
  战斗设计用「敌人伤害随回合增长」来给 value 定闹钟——拖得越久，tempo 越贵。
- **全信息公开是刻意的设计选择**：《杀戮尖塔》的成功被反复归因于「把一切都摊开给你看」
  （[RPS](https://www.rockpapershotgun.com/why-revealing-all-is-the-secret-of-slay-the-spires-success)），
  随机性放在「遇到谁/抽到什么」，不放在「这一下打多少」。**这条直接决定了 AI 可以走「求解」而不是「赌博」路线。**
- **组合深度 > 卡池数量**：设计文档里那句「depth is interactions, not raw card count」
  （[Design Codex](https://hayao.dev/docs/codex/genre-deckbuilder)）正好解释 BPH 为什么用**空间关系**制造 interaction——
  它把「卡牌组合」换成了「二维装箱 + 邻接图」。
- **负协同是特性不是 bug**：箭矢相邻失效、头盔不顶格失效、唯一性装备互相禁用。
  设计上保证「摆错要付代价」，所以 AI 必须能表达「归零」，不能只会加法。
- **平衡是一个胜率窗口**，不是单点：所以评测别只看「赢没赢」，要看「赢得多贵」（HP 损失、回合数）。

## 6. 对我们这套的判断

### 6.1 `policy.py` 的三个结构性缺陷

| 现状 | 问题 | 改法 |
|---|---|---|
| `ledger.estimate_damage(name)`：按**物品名**取均值 | 同一件物品的伤害取决于**摆位/锻造/状态**（Wooden Knife 右边有盾 +2；箭矢相邻直接失效） | 账本键改成 `(def, 有效属性快照)`；能从 `Item2` 直接读「当前有效值」就别用历史均值 |
| 逐步贪心：每次只挑当前分数最高的一个动作 | **顺序/预算耦合会翻车**。反例：A=1 费 5 伤、B=2 费 9 伤、能量 3。按比率先打 A（5/费），剩下 1 费打不出 B → 合计 5；最优是 B+A = 14 | 同一套估值，把「逐步贪心」换成「预算内枚举序列」——**估值不改也能立刻变强** |
| 击杀只在「清场」时加分（`lethal_bonus`） | 杀 1/2 个敌人没有价值，但它**少挨一整轮**，且敌人伤害还在涨 | 加 `kill_value ≈ 该敌人每回合输出 × 预计剩余回合`；顺带把「尖刺/召唤/治疗」纳入目标优先级 |
| `incoming_damage()` 只加 `type==attack` 的 power | 漏掉：毒/灼烧的 DoT、穿透（格挡白买）、尖刺（打它自己掉血）、多段 | 敌人意图解析成「伤害向量」，再算「需要多少格挡」；穿透/毒单独走「格挡无效」通道 |
| 濒死时把格挡乘 2 倍 | 死亡应该是**硬约束**，不是加权项；2 倍可能还是选输出 | 先做可行性过滤（这回合会不会死），再在可行集里最大化 |

### 6.2 实验已经做了（见 `SPIKE-07-combat-ab.md`）

同一套估值、只换决策过程，7200 个合成局面：贪心 **13.6%** 的回合价值缺口、19% 的回合一点伤害都没打；
「记住已挡掉的伤害」（1 行）→ 10.3%；再加「按每点能量选」（4 行）→ **4.9%**。
**单独加「按能量选」反而更差（14.1%）**——顺序很重要：先修格挡饱和，再谈性价比。

另外两个顺带发现：`data/state-log` 是探针快照（敌人/物品只落计数、legal 只有类型名），
**决策所需字段根本没落盘**；以及 buff 类物品在现框架里分数恒为 0，`choose` 直接 end_turn，
**投资型动作压根没进候选**（42 个含增伤物品的样例里，贪心用了 0 次，精确解用了 33 次）。

## 7. 建议路线

**Step 1 · 观测升级（1~2 天）**
把 `use_item` 的回执从「数值 delta」升级成**结构化事件**：谁对谁、造成多少伤害、被格挡多少、上了什么状态、
是否暴击/穿透、物品当时的**有效属性**。目标：每个 item def 都能攒出 `(context → effect)` 样本。

**Step 2 · 效果模型（3~5 天）**
wiki 的物品描述是**模板化**的（`On Use:` / `On Kill:` / `If there is a Shield to the right:` / `Per turn:`），
词条也是有限集合（Heavy/Float/Conductive/Ghostly/Projectile/Temporary/Pierce/Vampiric/Moveable/Transformable）。
先写模板解析器 + 关键词表 → 生成 DSL；解析不了的落回账本残差，并打「不确定」标签。
**验收：把一场录下来的战斗喂进模型，逐动作比对预测 vs 实际，准确率 ≥ 90% 才允许接求解器。**

**Step 3 · 回合求解器（3~5 天）**
DFS + 记忆化（键：能量、敌人 HP 向量、状态），带三个剪枝：能量上界、斩杀即停、支配剪枝。
输出不仅是动作，还有「为什么」（枚举了多少、次优差多少）——可解释性直接来自搜索。

**Step 4 · 战斗级价值（之后）**
目标函数从「赢」改成「HP 损失 + 回合数」。接入 `SpireBench` 那条教训：**别过度保血**，
在「不会死」的前提下，血是可以拿来换节奏的。

**评测口径**（沿用 MVP 的 A1–A6，但加两条）：
- 同种子 A/B：新策略 vs 旧策略，**胜率不变的前提下 HP 损失下降**（胜率会饱和，HP 不会）
- 模型保真度：逐动作预测准确率、按物品分层的错误率

## 8. 待实测（不要先下结论）

1. 战斗内**有没有伤害随机**（区间/暴击/命中）？有的话，单回合就不是完全确定，评估要取期望。
2. `use_item` 能不能**指定目标**？现在 `legal` 里没有 target 字段，而「杀谁」是斩杀线的核心。
3. 物品的**有效属性**能不能直接读（含布局/锻造/状态），还是只能自己推？这决定 Step 2 的工作量。
4. 敌人意图有没有**多段/条件**（例如「若你格挡则改为…」）？namu 只列了图标语义。
5. 重排（3 能量）到底值不值得建模？先量化「有多少局是因为摆位错误输的」再决定。
6. 状态结算顺序（多个 DoT、多个 on-kill 触发）——顺序会影响斩杀判定。
