# RESULT · 2026-10-30 · M4 真机 A/B（`--sustain` 开/关，各 3 局）

> 计划见 `docs/PLAN-item-census.md` §4 的 M4；上一轮只跑到「机制通了、样本不够」
> （`docs/RESULT-20261029-sustain.md`）。这一轮补齐 **3 局 vs 3 局**，并把
> 「每场掉血 / 最深楼层 / 等级」三件事真的量出来了。
>
> **一句话结论**：`--sustain` 在机制层面确认有效（3/3 局都吃到回血，对比组只有 1/3），
> **层数均值 1.3 → 1.7、出现本会话唯一一局「活满步数上限」**；但「每场掉血」没有变好
> （7.6 → 7.9），**差异仍在 1–2 局的方差之内，不能下「续航让人活更久」的结论**。

## 1. 怎么跑的

两臂只差一个 flag，其余完全相同：

```powershell
# A 臂（基线）
python agent\loop.py --focus-fire --aware-block --make-room 2 --max-steps 600 --max-seconds 1500

# B 臂（+ 续航）
python agent\loop.py --focus-fire --aware-block --sustain --make-room 2 --max-steps 600 --max-seconds 1500
```

- **一局一次进程**：不传 `--auto-retry`，`loop.py` 死了就退出，避免跨局统计污染
  （PITFALLS 里那条「采样器跨局继续写同一个文件」的坑）。
- 每局之间用 `retry_run` 重开新局，**同一个游戏进程**，不重启游戏 → 两臂的启动条件一致。
- `--max-steps 600`：上一轮最长 175 步；这一轮 B 组有一局撞到 600 步上限（见下），
  所以后续实验应把上限抬到 1000+，否则会把「活得久」截断成「步数用完」。
- 汇总脚本是本轮新增的 `tools/ab_m4.py`（只读日志）：

```powershell
python tools\ab_m4.py data\runs\ab --verbose --json data\runs\ab\summary.json
```

## 4. 结论（按可信度排序）

1. **`--sustain` 的触发是可靠的，而且是「频率」上的改善**：B 组 **3/3 局**都吃到回血
   （10 / 13 / 8），A 组只有 **1/3 局**（15，其中 5 还来自事件而不是食物）。
   每局真正走 `sustain=` 分支的是 1 次：

   ```
   B1: WARM DRINK sustain=10/10hp(hp=25/40) worth=+10.00   -> +10
   B2: BLUEFIN    sustain=8/8hp(hp=29/40)  worth=+8.00    -> +8
   B3: BLUEFIN    sustain=8/8hp(hp=32/40)  worth=+8.00    -> +8
   ```

2. **层数 1.3 → 1.7，且出现唯一一局活满 600 步**（B2：floor 2、hp 16、**9 场战斗**）。
   9 场是全部 6 局里最多的——不是靠躲，是靠回血把战斗数堆上去的。
   **但 B2 是「撞上限」而不是「通关」**，只能算「活得久」，不能算「赢了」。

3. **「每场掉血」没有变好**：7.6 → 7.9（非致命场 6.9 → 4.8）。
   两个方向相反的信号同时存在，说明**这个指标在 n=3 下没有分辨力**：
   一个 34 血的致命场就能让 B 组的均值反超。

4. **不能下的结论**：`--sustain` 让人活更久 / 更耐打。现在的证据只支持
   「回血确实会发生、且比基线稳定」，**不支持**「因此整体表现更好」。

## 5. 顺手量出来的三件事（可能比 sustain 更值钱）

1. **非战斗掉血比想象中大**：A 组 11.3 血/局，B 组 7.0（`finish_reorganize` 这条路径
   一次能掉 3–8）。A2/A3 两局**非战斗掉血 29 血，占了总掉血的 1/3**。
   → 和 HANDOFF 里「整理阶段掉血是另一个大头」的判断一致，`GetDamageForHazards`
   值得单独查。
2. **死亡几乎总发生在多敌房，且是单场爆发**：致命场掉血 17 / 14 / 5（A）、
   34 / 12 / 23（B）。B1 前 4 场一共只掉 2 血，第 5 场一次掉 34——
   **续航救不了这种局**，需要的是「多敌房风险分级」（原计划第 3 项）。
3. **零伤回合 26% → 22%**，方向对但差异同样在方差内。

## 7. 局限 / 下一轮怎么改

| 问题 | 影响 | 下一轮怎么修 |
|---|---|---|
| **n=3 太小** | 层数差 0.4、掉血差 0.3 都在噪声里 | 每臂 6 局起；或先修下面两条，让信号变大 |
| **600 步上限截断** | B2 的「活满」其实是 censored | 上限抬到 1200–1500，或改成「打完 floor 3 才停」 |
| **致命场污染每场掉血** | 一个 34 血异常值翻转结论 | 已加「非致命/场」列；后续主指标用它 |
| **食物供给不可控** | B 组每局只有 1 次 sustain 触发 | 先看战利品里食物出现率（配额 3 件里有没有食物） |
| **每回合护甲还没进战斗打分** | `block_per_turn` 只用于丢弃估值 | 按「预计还剩几回合」折现后再进 A/B |

**建议的下一步顺序**：①修整理阶段掉血（可能比续航更值钱）；②多敌房风险分级；
③回来用 6+6 局重跑这一套 A/B（脚本已经现成）。
